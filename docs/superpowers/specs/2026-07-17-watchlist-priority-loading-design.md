# 觀察頁 AI 資料優先載入設計

## 背景與目標

觀察頁目前以四個並行工作序列，依觀察名單原始順序逐檔抓取 AI 量化資料。使用者最常先查看「AI進場」股票，再依序查看「超高度」、「高度」與「出場後再進場」；原始順序可能讓 AI中立、中度等較低優先資料先占用載入時間。

本次調整只改變 AI 量化資料的抓取順序，不改變篩選結果、卡片內容、資料來源、快取有效性或完整更新範圍。目標是讓常用分類較早出現最新資料，其餘分類繼續在背景補齊。

## 載入優先順序

使用上一份可用的本機、雲端或目前畫面快取分類，依下列順序建立佇列：

1. AI進場且推薦等級為超高度
2. AI進場且推薦等級為高度
3. 出場後再進場
4. 其他股票，包括 AI進場中度或低度、AI中立、AI出場及無分類資料

同一優先層級維持原觀察名單順序，避免每次載入時順序無故跳動。若完全沒有舊分類資料，所有股票歸入第四層，行為等同目前的原始順序。

「出場後再進場」若同時符合前兩個 AI進場層級，仍以較高的 AI進場推薦等級優先，避免同一股票重複排隊。

## 架構與資料流

新增一個不依賴 React 狀態的純排序工具，輸入觀察名單與上一份 `quantDataMap`，輸出穩定排序後的觀察名單。排序工具只讀取：

- `currentSignal` 判斷 AI進場
- `aiQuanBackDataComment.remark` 判斷超高度與高度
- `reentryAfterExit.hasReentry` 判斷出場後再進場

觀察頁開始完整 AI 同步時，先對目前可用的 `quantDataMap` 建立快照，再清理畫面上的同步狀態。四個既有工作序列共同消耗已排序佇列，維持目前最多四檔並行的限制。每檔成功後立即更新該股票的量化資料與推薦卡片；失敗、逾時與進度計數沿用現有行為。

快取直接命中時仍先立即顯示快取，不新增阻塞。只有需要逐檔同步 AI 資料時才套用優先佇列。手動「重新抓取」也使用畫面中同步前的舊分類排序，但仍抓完全部股票。

## 錯誤與邊界處理

- 缺少上一份量化資料：排入其他分類，維持原順序。
- 推薦文字不存在或格式未知：不猜測推薦等級，排入其他分類。
- 單檔請求失敗或超過既有 12 秒限制：標記失敗並繼續下一檔，不阻塞其他優先分類。
- 最新資料使股票分類改變：立即反映最新分類；本次已建立的剩餘佇列不重新洗牌，避免並行競態與畫面不穩定。下次同步會使用新分類。
- 使用者切換篩選按鈕：只影響顯示結果，不動態改寫正在執行的佇列。

## 測試策略

先為純排序工具建立 Node 測試，確認：

1. `AI進場＋超高度` 早於 `AI進場＋高度`。
2. `AI進場＋高度` 早於 `出場後再進場`。
3. 其他分類最後載入。
4. 同級股票保持原觀察名單順序。
5. 缺少或未知舊資料時保持原順序。
6. 同時符合多項條件的股票只出現一次，並採最高優先級。

實作後執行排序工具測試與完整 `npm run build`。既有專案 lint 有歷史性非本次錯誤，因此完成判定以新增測試、TypeScript 編譯與 Vite 正式建置為主。

## 完成條件

- 冷啟動且有舊快取時，逐檔 AI 請求依指定優先順序開始。
- 完全沒有舊快取時，不改變原載入順序。
- 每檔資料完成即更新，低優先資料繼續背景載入至全部完成。
- 篩選數量、篩選結果、手動重新抓取與錯誤狀態維持正確。
- 新增排序測試通過，正式建置成功。

## 不在本次範圍

- 不變更預設選取的篩選按鈕。
- 不依使用者即時點擊動態插隊。
- 不調整 API、Supabase 結構、每日更新時間或快取期限。
- 不提高並行請求數量。
